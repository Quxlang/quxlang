# Quxlang I/O Phillosophy

1. The underlying async API should optimize for "operation" objects, of which a unique operation object exists for each type of operation, e.g. `epoll_file_read` or `io_uring_file_write`. Generic dispatch from e.g. `io::file_ref::read` can then create an operation of the appropriate type for the configured IO runtime.
2. The coroutine and therefore underlying async APIs are designed to "run to unconditional completion". This means we do not support instant cancellation or dropped coroutine frames. If an I/O operation is started, the continuation MUST run, even if that continuation just produces an exception.
3. Each I/O operation should "run to completion" and unconditionally trigger the associated coroutine continuation. Operation cancellation, where supported, produces a result with an "operation cancelled" result or exception. 
4. IO types are divided into ARMO (automatic resource management objects) e.g. `io::file` or `net::tcp_connection` and RRO (resource reference objects) e.g. `io::file_ref` or `net::tcp_connection_ref`. Both the ARMO and RRO are thin handles over the OS-native io descriptor that provide type safety. They do not contain other fields like a pointer to an I/O context or similar, so they can both do native I/O with zero overhead. Where an I/O runtime or thread pool needs to be involved, it can either be provided contextually (e.g. by a coroutine controller) or as an explicit argument to the I/O functions. The difference between the ARMO and RRO versions is that e.g. the ARMO version will automatically call close and provides a move-only API, whereas the RRO `_ref` variants are freely copyable and do not.
5. Generally, we should aim for efficiency, but not at the expense of latency, othogonality or predictability. For example, it might produce better performance to batch system call submission together, but in some cases that could produce a deadlock if e.g. we're waiting on a mutex that requires that I/O to complete. To get better efficiency, the default should likely be the most general version with additional classes exposed for performance optimization where possible. e.g. one might provide a class such as `io::io_batcher` to batch multiple io operations together for submission to io_uring.
6. If we implement optimization classes such as but not limited to e.g. `io::io_batcher`, they should expose platform details or depend on the presence of a supported backend. For example, `io::io_batcher` would need to support backend systems which don't support batched I/O. We focus on the programmer contract, and implement it the most efficient way possible for each backend.
7. We should always pay special attention to our I/O design, both from an ergonomics perspective and also an efficiency perspective. We stive to provide APIs that are simple to use, general, predictable, and high performance.
8. We generally don't provide "leaky" abstractions that expose platform details to the programmer. We focus on unified abstractions that translate to efficient zero-overhead code on all supported platforms. Sometimes that involves tradeoffs between different approaches which are more or less efficient on different platforms. It's preferrable to produce multiple different APIs which abstract away platform differences to patch over differences, even if some are more or less efficient on some backends.
9. Quxlang's instance allocator for compile-time sized allocations is _extremely fast_. Conventional wisdom around allocations from languages like C and C++ usually does not apply. Expect short lived allocation/free pairs in the range of ~2ns. Most haphazard "allocation free" strategies are actually _slower_. As a rule of thumb, the cost of an allocation on the fast path is two (or one combined) L1 loads, a highly predicatable branch, and a writeback store. Introducing virtually _any_ complexity to avoid an allocation will usually make the code _slower_.
